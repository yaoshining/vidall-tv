# 媒体库异步加载会话回归

## 触发条件与调用链

`MediaLibraryTab.aboutToAppear` 的数据库 ready 回调、
`onMediaDataVersionChange` 的刮削完成通知，以及 `loadActiveSourceContent`
都会调用 `reload()`。播放器保存进度事件还会独立调用 `loadContinueWatching()`。
原来的 `reload()` 强制清除 `isLoading`，没有使旧查询失效：旧结果能覆盖新列表、
统计与未观看数据，旧任务的 finally 也会提前结束新任务的 loading。
继续观看中途写入电影进度映射、失败时清空列表，同样存在过期写入和部分提交。

## 刷新语义

- 每次 `load()` / `reload()` 都立即启动一个新会话，不因正在加载而丢弃请求。
  在途数据库查询不强制取消；它恢复时检测会话，过期则停止后续查询及提交。
- 最新主会话全部查询成功后同步提交主列表、统计、未观看、评分与年代数据。
  只有最新主会话可以结束 `isLoading`；`isLoaded` 表示已有成功加载的数据，
  首次失败保持 false，后续刷新失败保留 true 和上次完整数据。
- 未观看查询失败不再用全部最近添加内容冒充未观看；整次主库快照保留供重试。
- 继续观看使用自己的请求序号和主库会话号，列表与电影进度映射一起提交。
  主库开始刷新会使此前的进度查询失效；主库成功提交后重新查询进度，
  使加载期间基于旧元数据启动的进度任务失效。进度查询不阻塞主库 loading。
- 当前失败保留已有有效数据，并沿用日志错误反馈；过期失败不输出错误。
  每个返回的 Promise 对应本次调用结束，不承诺等待后来发起的其他刷新。


测试转译并执行真实 `MediaLibraryModel.ets`，只替换数据库、装饰器和设备依赖的工具边界。
通过显式 resolve/reject 和查询进入信号控制顺序，不使用定时 sleep。
共 31 项：九个主查询点的晚到响应、九个查询点失败保留数据、过期失败、loading 所有权、
连续 load/reload、首次失败重试、主库与进度事件交错、进度失败重试，以及新旧剧集格式的
电视剧和单集元数据查询交错。测试只验证会话提交与错误处理，不验证数据库 SQL 或播放器。

CI 工作流 `媒体库加载竞态回归` 在主机上运行这组测试；已有设备单测、集成测试及门禁不变。
主机测试不等同于 ArkTS 编译、设备验证或真实数据库验证；构建和设备 CI 需分别查看对应提交。
