## Context

参见 `proposal.md` 的动机与范围。当前扫描适配器直接调用 `VideoScrapeProcessor`，媒体库的全局重新刮削又在页面中维护一套相近写库逻辑；现有 `ScrapeClient` 有会话内系列缓存，`AppPreferences` 已提供刮削并发数。Home TopBar 目前右侧仅包含时钟和品牌区，页面状态普遍通过单例 Store/Model 暴露给 ArkUI V2 组件。

实现受 ArkTS 严格类型约束：禁止 `any`/`unknown`、匿名未类型化对象和 catch 类型注解，`build()` 只能包含 UI 组件语法。任务不能持有页面实例或页面回调，否则页面离开后会产生失效引用。

## Goals / Non-Goals

**Goals:**

- 建立一个所有局部与全局入口都能复用的范围化刮削核心和任务执行协议。
- 以有限并发后台队列隔离耗时网络/数据库工作与 UI 生命周期。
- 让任务状态成为全局单一事实来源，驱动 TopBar 角标、下拉列表、候选确认及媒体数据刷新。
- 保证取消、重试、部分失败和页面销毁场景下的数据一致性及 TV 焦点连续性。

**Non-Goals:**

- 不为 Jellyfin/Plex 等影视服务器实现本地刮削。
- 不提供正在执行任务的抢占式取消，也不承诺应用进程被系统终止后的任务恢复。
- 不修改第三方刮削 Provider 协议，不引入新的外部依赖。
- 不在本次变更中归档 OpenSpec；归档等待用户明确通知。

## Decisions

### 1. 目标描述、核心执行与队列调度分层

使用显式判别类型描述电影、系列、季、单集、文件夹和全局目标，并为每个任务显式携带 `incremental`、`fix-missing` 或 `overwrite` 处理模式。范围解析器只把目标转换为规范化视频集合；范围化服务先在范围内按当前全局入口语义筛选目标，再负责候选搜索、选择应用、持久化和逐项结果；队列只负责生命周期、并发槽和状态快照。

选择该分层是为了让页面入口只组装目标并入队，同时让全局扫描和局部入口共享业务规则。替代方案是在各页面调用扫描器并传范围参数，但这会继续复制确认、写库和错误保护逻辑。

### 2. 单例队列配合只读可观察 Store

队列作为应用进程内单例拥有任务和调度器；可观察 Store 向 ArkUI 暴露任务快照、活动数量及弹层可见性。UI 不直接修改任务对象，只通过 `enqueue/cancel/retry/clear/resolveCandidate` 命令改变状态。

相比把任务存入页面 `@Local`，单例不依赖触发页面生命周期。相比立即持久化完整队列，本期不承诺进程重启恢复，避免引入任务参数迁移和敏感凭据持久化；终态记录仅保留在当前应用会话，用户可手动清除，并设置有界历史数量防止内存增长。

### 3. 并发按任务槽控制，任务内部复用现有抓取限制

队列并发上限从现有刮削并发偏好读取并钳制为安全正整数。调度遵循 FIFO；一个任务占一个槽，任务内部逐组推进并复用底层既有网络/播放器限制，避免任务数与文件数形成乘法并发。进入候选确认前保存续执行上下文、切换为等待确认并释放槽；用户选择后重新进入等待队列。

替代方案是所有文件组成一个全局工作池，吞吐量更高但会破坏任务级进度、取消和系列候选复用，且数据库写入更难隔离。

### 4. 活动任务使用规范键去重

入队时由目标类型、文件源、规范化目标标识、处理模式和候选策略生成稳定键。相同范围的不同处理模式可分别入队；等待中、进行中及等待确认均视为活动。等价键已存在时返回现有任务 ID，并打开任务列表。终态不阻止新任务。

重试创建新执行记录并引用来源任务，只携带失败或未处理目标；这样保留原结果审计，同时避免重复覆盖成功项。替代方案是原地重置失败任务，但会丢失前次结果并让 UI 状态倒退。

### 5. 候选确认是队列状态而非页面控制流

范围化服务遇到需要确认的媒体组时返回强类型暂停结果，队列保存媒体组、候选和续执行游标。全局候选弹层观察等待确认任务并调用队列命令恢复或取消当前组；不通过 Promise 长期捕获页面回调。

整剧、整季和混合文件夹按系列搜索键聚合，确认一次后缓存系列候选并按季集号应用。全局任务显式使用自动策略，完全绕过确认状态。

### 6. 写库以单项目标为一致性边界

复用并下沉现有分类、候选详情获取、三种模式判断和 DAO 写入规则。“新增和已修改”仅处理范围内新增文件、文件指纹发生变化或尚无完整刮削关联的目标；“缺少元数据”仅处理关联或海报等必需元数据不完整的目标；“覆盖”处理范围内全部目标。每个媒体目标在获得完整新数据后才执行关联更新；失败不预先删除旧记录。覆盖模式只在成功生成替代数据时替换目标关联，且不得触及范围外视频。

不采用整任务数据库事务，因为网络请求和用户确认可能持续很久，长事务会锁住数据库；任务结果允许部分成功并准确汇总。

### 7. 通过全局媒体数据版本刷新页面

成功提交后递增按领域划分的媒体数据版本（至少覆盖媒体库、电影详情、剧集/季详情）。相关 Store/页面观察版本或在 `aboutToAppear` 比较版本后重新查询。任务仅发布目标标识及版本变化，不保存页面回调。

相比直接调用触发页刷新函数，该方式支持页面已销毁、多个页面同时缓存以及从 TopBar 重试任务的场景。

### 8. TopBar 使用锚定弹层和状态派生角标

在时钟左侧放置独立 `ScrapeTaskIndicator`。角标由 Store 每次从任务快照派生，仅统计等待中和进行中，避免维护第二份计数。点击后打开锚定下拉组件，按状态优先级和创建时间排序；操作按钮根据状态决定是否显示。返回键关闭并通过稳定组件 ID 请求焦点回到图标。

候选选择使用独立全局弹层，其层级高于任务列表；打开候选时先关闭任务下拉，防止双弹层焦点竞争。

## Risks / Trade-offs

- [任务内部逐组处理可能降低峰值吞吐] → 以可配置的任务级有限并发平衡吞吐和稳定性，并通过进度反馈降低等待不确定性。
- [等待确认任务长期滞留] → 不占执行槽、不计活动角标，但保留在列表顶部并明确“等待确认”；用户可进入候选或取消当前媒体组。
- [应用进程终止会丢失队列历史和未完成任务] → 本期明确为进程内队列；已完成写库按单项提交保留，后续可基于稳定任务 DTO 增加恢复能力。
- [多个范围重叠但规范键不同会重复处理同一视频] → 入队先做等价目标去重，执行前再次读取最新元数据并按模式判断；不对任意重叠集合做昂贵全局锁定。
- [全局事件引发过多页面查询] → 按领域和目标标识发布版本，页面只在相关版本变化时刷新，并合并短时间内连续通知。
- [任务历史导致内存增长] → 终态历史使用有界集合，优先清理最旧的已完成/已取消记录，失败记录保留到用户清除或达到上限。

## Migration Plan

1. 先补充范围目标、结果 DTO、DAO 范围查询和统一刮削服务，不切换现有入口。
2. 引入队列与可观察 Store，通过测试执行模拟任务，验证状态机、并发、暂停和重试。
3. 接入 TopBar 指示器、任务列表和候选弹层，再逐个接入五类局部入口；每个入口先选择“新增和已修改”“缺少元数据”或“覆盖”，覆盖模式入队前显示危险确认。
4. 最后迁移全局三种模式调用，保留原危险确认；确认局部与全局模式语义及新旧结果一致后移除页面内重复写库逻辑。
5. 若出现回归，可暂时隐藏局部入口和 TopBar 图标，并将全局入口回退到原调用路径；新增服务和 DTO 不改变已有数据库结构，可安全保留。
6. 实施完成后执行 OpenSpec verify，但不得执行 archive，直到用户另行明确通知。
